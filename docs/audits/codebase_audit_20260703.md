### [CRITICAL] Configured perp funding rate is never charged: 0.0 sentinel from get_latest_bar_value shadows the static default (and kills the require_funding_coverage gate)
- Where: `src/lumina_quant/backtesting/portfolio_backtest.py:641`  (lens: backtest-fidelity, category: cost model / funding)
- Detail: _resolve_funding_rate tries per-bar data first: `fallback = self.bars.get_latest_bar_value(symbol, "funding_rate")`. HistoricCSVDataHandler.get_latest_bar_value (data.py:426-433) returns 0.0 — not None — when the column/feature is absent, so the `if fallback is not None: return float(fallback)` branch (portfolio_backtest.py:644-646) returns 0.0 on every bar. The configured non-zero `execution.funding_rate_per_8h` default (line 653) and the `require_funding_coverage` ValueError (line 660) are both unreachable for any run on HistoricCSVDataHandler or its windowed-parquet subclass. PROVEN by micro-run: config FUNDING_RATE_PER_8H=1e-4, long 10 units held 30h => total_funding_paid=0.0, expected 0.30; _resolve_funding_rate returned 0.0. The comment at lines 623-627 explicitly states 0.0 must not be conflated with 'absent', but the data-handler API does exactly that.
- Impact: Every leveraged perp backtest silently pays zero funding unless a real funding_rate feature series exists in the feature DB — carry/momentum strategies that hold positions across funding intervals show inflated Sharpe (funding is often 10-30%/yr of notional cost on crowded perps). The audit-hardening require_funding_coverage flag also can never fire on this path, so turning it ON gives false assurance.
- Suggested fix: In _resolve_funding_rate, do not use get_latest_bar_value's 0.0-defaulting API for presence detection: check `"funding_rate" in self.bars.col_idx` (or add a get_bar_value_or_none API) before trusting the fallback; only treat a value as present when the column genuinely exists.

### [CRITICAL] reduce_only is never enforced at fill application — double exits and post-liquidation bracket orders flip a flat position into a phantom opposite position
- Where: `src/lumina_quant/backtesting/portfolio_backtest.py:390`  (lens: backtest-fidelity, category: fill realism / order lifecycle)
- Detail: update_positions_from_fill/update_holdings_from_fill apply any FillEvent unconditionally; SimulatedExecutionHandler.check_open_orders (execution_sim.py:336-617) fills triggered orders without consulting the portfolio position, and the reduce_only flag is only transported (events.py:92), never enforced. Two realizable engine paths: (a) In handle_market_event the SIGNAL is queued before the FILL from check_open_orders (engine.py:189 vs 196; queue is FIFO), so an EXIT signal on the same bar as a protective-STOP trigger sizes its reduce-only order from the PRE-fill quantity, and both fills apply — PROVEN by micro-run: long 10 -> stop fill -> 0 -> 'reduce-only' exit fill -> -10 phantom short. (b) Portfolio._check_liquidations (lines 780-816) emits the liquidation FillEvent but never cancels the position's protective SL/TP/TRAIL orders in execution_handler.active_orders (only reduce_only MKT/LMT placement cancels brackets, execution_sim.py:241-245), so a leftover bracket later fires from flat and opens an unintended position.
- Impact: Backtests can carry phantom short/long positions that a live exchange would reject (Binance reduces/rejects reduce-only orders exceeding position). PnL after any same-bar stop+exit coincidence or any liquidation diverges arbitrarily from live — a 'flat' strategy can be secretly short through a rally, corrupting equity, drawdown, and optimizer selection.
- Suggested fix: Clamp reduce_only fills to min(order qty, |current position| on the matching side) at fill time (emit partial/no-op fills), and have _check_liquidations notify the execution handler to cancel all working orders for the liquidated symbol/side.

### [CRITICAL] Retry-on-5xx resubmits the same order: documented Binance 'unknown outcome' path can double-send real positions
- Where: `src/lumina_quant/live/execution_live.py:1496`  (lens: live-readiness, category: order lifecycle / idempotency)
- Detail: execute_order submits via _call_with_retry(self.order_gateway.submit, ..., retries=3) (execution_live.py:1496-1506). _is_retryable_exception (lines 49-64) treats HTTP 429/500/502/503/504 as retryable, and BinanceFuturesAPIError carries status_code (binance_futures_client.py:165-170). Binance explicitly documents that a 5XX response means execution status is UNKNOWN and may have succeeded. The retry re-calls submit with the same params dict; newClientOrderId is forwarded (binance_futures_exchange.py:447,463-466) but on Binance USDT-M futures newClientOrderId is only 'unique among OPEN orders' — an order that filled immediately (any MKT order, or a marketable LMT) is no longer open, so the retried submit with the same client id is ACCEPTED as a brand-new order. There is no query-by-clientOrderId reconciliation before retrying.
- Impact: Real money: exchange returns 502 while the first order actually executes and fills; 1s later the retry places a second identical order → position is doubled (and for reduce-only flatten orders, the second one flips or is rejected). Local tracker only knows the second order_id; the first order's fill arrives as a synthetic untracked order. This is the classic double-send bug that loses money on the first busy day.
- Suggested fix: On retryable submit failure, first query open/recent orders by clientOrderId (GET /fapi/v1/order with origClientOrderId) and adopt the existing order instead of resubmitting; only resubmit when the query proves the order never reached the engine.

### [CRITICAL] FLATTEN kill-switch sends one batch of GTC limit orders and never retries; default config forbids market escalation
- Where: `src/lumina_quant/live/trader.py:1267`  (lens: live-readiness, category: risk controls / kill-switch)
- Detail: _evaluate_risk_guards (trader.py:1267-1273) sets _flatten_inflight=True after the first _flatten_all_positions call and skips all further flatten attempts while the breach persists; the flag resets only when risk PASSES (line 1257), which cannot happen while positions remain. With schema defaults default_order_type='LMT', allow_market_orders=False, limit_time_in_force='GTC' (schema.py:258-263), _reduce_only_order_policy_fields prices the flatten one tick worse than the LAST BAR CLOSE (trader.py:1126-1136). In polling mode check_open_orders cancels the unfilled flatten after ORDER_TIMEOUT (default 10s, execution_live.py:1589-1599) and nothing re-issues it. Legs with no positive reference price are silently skipped (trader.py:1113-1119, returns False).
- Impact: Exactly in the scenario the hard-drawdown/kill-switch exists for (fast crash, price gapping away from last close), the reduce-only limit orders never fill, get timeout-canceled, and the account stays fully exposed while the trader believes flatten is 'inflight'. Max-daily-loss / hard-drawdown limits are therefore not actually enforceable de-risking.
- Suggested fix: Track flatten order outcomes: if flatten orders terminal without full close, re-issue with progressively more aggressive pricing and finally an explicit market/IOC escape hatch that bypasses allow_market_orders for reduce-only kill-switch orders; never leave _flatten_inflight latched on canceled/timed-out flattens.

### [CRITICAL] Daily-loss/drawdown guards measure against config INITIAL_CAPITAL, and equity/cash is never re-synced with the exchange after startup
- Where: `src/lumina_quant/live/trader.py:1294`  (lens: live-readiness, category: reconciliation / risk baseline)
- Detail: Portfolio.__init__ sets day_start_equity = initial_capital = config trading.initial_capital (default 10000.0, schema.py:34; portfolio_backtest.py:78). _sync_portfolio (called once in run(), trader.py:1713) overwrites cash and initial_capital with the real balance (trader.py:1291-1295) but NOT day_start_equity, and _update_day_boundary only resets it at the next UTC day rollover (portfolio_backtest.py:548). RiskManager.evaluate_portfolio_risk computes intraday_loss_pct against this stale baseline (risk_manager.py:185-188). Additionally, after startup nothing ever re-reads exchange balance: funding payments, real commissions, and liquidations only land in runtime_cache via user-stream balance events (trader.py:770-794) and never touch portfolio.current_holdings, which drives every kill-switch and exposure cap.
- Impact: First real run with a 2,000 USDT account and default initial_capital=10000: day_start=10000 vs equity≈2000 → 80% 'intraday loss' → immediate FREEZE or hard FLATTEN of live positions at startup. Opposite mismatch (account >> config) makes max_daily_loss_pct effectively unreachable. Long-running perp positions accumulating funding drain drift local equity upward vs reality, so loss limits trip late or never — no funding-blowout handling exists anywhere in the live path.
- Suggested fix: Set day_start_equity (and equity high-water state) from the reconciled exchange equity in _sync_portfolio; add a periodic balance/equity reconciliation (reuse RECONCILIATION_INTERVAL_SEC) that folds exchange wallet balance + unrealized PnL and funding/commission deltas into current_holdings, alerting on divergence beyond a threshold.

### [CRITICAL] _kama recomputes full-history KAMA (O(n*period)+O(n^2) slicing) up to 3x per bar per symbol
- Where: `src/lumina_quant/strategies/return_rider_alpha_sleeves.py:110`  (lens: compute-hotpaths, category: redundant recompute in per-bar hot loop)
- Detail: Measured with cProfile (5,000 bars, 1 symbol): AdaptiveTrendRiderStrategy._process_symbol costs 335 us/bar/symbol and the _kama chain is 4.5s of 7.0s (64%). _kama iterates the ENTIRE 248-bar ring buffer from vals[0] on every call, and each iteration does `vals[: idx + 1][-(period_i + 1):]` (line 111) — the first slice copies idx elements, making the loop O(n^2) — then calls kaufman_efficiency_ratio (689,576 calls for 5,000 bars, ~138/bar). _kama_now_prev (line 596) calls _kama TWICE per gate (now + prev), and it runs in _entry_decision every flat bar and _should_pyramid every in-position bar; _entry_metadata recomputes the ER a third time on entry. Cost scales super-linearly with history: measured 0.37 ms/call at n=250, 2.06 ms at n=1000, 17.3 ms at n=4000 — and history_size = max(atr_period, vol_window, max_hold_bars, kama windows)+8 (line 247), where max_hold_bars is TUNABLE up to 200,000 (line 569), so one optimizer draw can make _kama minutes-per-bar.
- Impact: Candidate evaluation of this sleeve over 100k 30m bars burns ~33 s/candidate/symbol on redundant KAMA recompute alone; a strategy-factory sweep of hundreds of candidates x folds x symbols turns into hours of pure waste, and any trial with large max_hold_bars effectively hangs the fold. Live 30m cadence is unaffected functionally but wastes the same CPU per decision.
- Suggested fix: Two stages: (1) byte-identical now: replace the slice with `vals[max(0, idx - period_i): idx + 1]` (verified identical output, removes the O(n^2) copy; 1.4x at n=248, far more at large n). (2) config-gated (repo golden-byte rule): keep an incremental KAMA + rolling |diff| ER accumulator in _RiderState updated O(1) per accepted bar keyed by time_key, and store a small deque of recent KAMA values so _kama_now_prev's `prev` is a lookup instead of a second full recompute.

### [CRITICAL] Backtest data handler materializes entire OHLCV dataset as Python object tuples (~323 B/row, 6.7x numpy) — 'windowed' handler windows emission only, not storage
- Where: `src/lumina_quant/backtesting/data.py:176`  (lens: memory, category: memory/data-loading)
- Detail: HistoricCSVDataHandler._open_convert_csv_files does `rows = tuple(df.iter_rows(named=False))` (data.py:176, 196) and stores the full history in self.symbol_rows[s] (line 202) plus a parallel Python list of int timestamps in symbol_timestamps_ms (line 210). HistoricParquetWindowedDataHandler (data_windowed_parquet.py) inherits this: its deque(maxlen) `_window_rows` only bounds the emitted MARKET_WINDOW snapshot; the full chunk stays resident as Python tuples, and `_freeze_rows_as_epoch_ms` (data_windowed_parquet.py:88) builds a second full tuple per symbol transiently. Measured with .venv/bin/python + resource.getrusage: 86,400 1s rows + timestamp list = 26.6 MiB -> 323 B/row vs 48 B/row for a float64 array (6.7x overhead).
- Impact: At the default chunk_days=2 (configuration/schema.py:177) a 110-symbol 1s universe needs ~5.7 GiB of bar tuples per chunk — already at the repo's own ExecutionMemoryPolicy heavy_run_cap_gib=6.5 / 8 GiB cap (core/memory_budget.py), so heavy runs trip MemoryCapExceededError or OOM before strategy code runs. A 30-day chunk is ~86 GiB; a single symbol-year of 1s data is ~9.5 GiB. This directly caps universe size and chunk length for backtest validity work.
- Suggested fix: Keep per-symbol history as contiguous numpy arrays (or the Polars frame) and yield row tuples lazily at the cursor (only next_bar and the bounded window deques need tuple form); symbol_timestamps_ms can be an int64 array. This cuts steady-state load ~6-7x with no behavior change to emitted events.

### [MAJOR] Funding intervals are anchored to position-entry time, not exchange funding timestamps — sub-8h holds never pay funding
- Where: `src/lumina_quant/backtesting/portfolio_backtest.py:588`  (lens: backtest-fidelity, category: cost model / funding)
- Detail: _apply_funding sets `self._last_funding_ts[symbol] = now_ts` on the first bar a position is held (line 588-590) and then charges `periods = (now_ts - last_ts) // interval_seconds` (line 594). Real USDT-M perps charge funding at fixed clock times (00:00/08:00/16:00 UTC) to whoever holds the position at that instant. A position opened 07:00 and closed 09:00 UTC pays one funding event live but zero here (elapsed 2h < 8h); symmetrically, a position opened 08:01 and held to 15:59 pays here-nothing live-nothing (ok) but 16:01-entry to next-day 00:01 pays 1 live vs 0 here. Any strategy whose hold time is under 8h pays exactly zero funding in backtest regardless of how many funding timestamps it straddles. Also, multi-period catch-ups are all priced at the current close rather than each interval's price.
- Impact: Intraday perp strategies (hold 1-8h) that systematically hold through the 00/08/16 UTC funding marks show zero funding cost in backtest while paying (or receiving) it live — biased strategy selection toward exactly the holding windows the simulator misprices.
- Suggested fix: Charge funding when the bar clock crosses k*interval boundaries in epoch time (floor(now/interval) > floor(last/interval)), independent of entry time; anchor last_funding_ts to the boundary, not to entry.

### [MAJOR] No client-side rate limiting, no 418 handling, and no server-time sync in the Binance REST client
- Where: `src/lumina_quant/exchanges/binance_futures_client.py:126`  (lens: live-readiness, category: API robustness)
- Detail: BinanceFuturesRESTClient sets rateLimit=0 (line 61) and _request has no weight budget, throttle, or Retry-After handling; check_open_orders and reconcile_open_orders issue one signed query_order per tracked order per loop with _call_with_retry retrying 429s after 1-2s (execution_live.py:132-150), and HTTP 418 (Binance IP auto-ban after repeated 429s) is neither in the retryable status set nor specially handled. ### [MAJOR] Production batch factor-IC runs the 'python_loop' strawman arm; the numpy-batched arm (28.5x faster, proven in-repo) was never adopted
